Round 3 (coordinator's Android check of f460184, screenshots outside the repo):
1. **Theme didn't re-style the open page (AC2).** On the Appearance page, tapping Dark checked the chip, but the page, header, card and tab bar stayed light until another screen was opened (and the same for Light). Cause: RN 0.88's `Appearance.setColorScheme` only updates JS's cached value and waits for Android's configuration-change event (`appearanceChanged`) to notify `useColorScheme` subscribers. That event didn't arrive, so mounted consumers of `useTheme` (UiProvider's colour variables, the Settings header, the tab bar) never re-rendered. Jest missed it because the Appearance mock emits `change` from `setColorScheme` and the other tests spied it out. Fix (spec D14): `setColorSchemePreference` in `src/theme/use-theme.ts` is read by `useTheme` through `useSyncExternalStore`, so every consumer re-renders in the same pass. `AppearanceSync` and `applyStoredAppearance` use it, and the root StatusBar style follows `useTheme`. Regression tests: `use-theme.test.tsx` "applies the in-app choice to mounted screens at once, with no Appearance event", "an in-app choice wins over the device until it is set back to system"; `settings-routes.test.tsx` checks UiProvider's variables flip dark → light while the Appearance page stays mounted. Mutation check: with `AppearanceSync` reverted to `Appearance.setColorScheme`, the route test fails.
2. **"Add a task" clipped to "Add a" after a theme switch.** The button was full width but its label box was one line narrower than the drawn text, so the last word wrapped onto a hidden second line. It appeared only after a switch through `Appearance.setColorScheme`, which on Android runs `AppCompatDelegate.setDefaultNightMode` and changes the Activity configuration under already-measured text. The outlined button's label was re-measured after that change (its border style is recomputed with the new variables) and got a box that doesn't match what is drawn. This cause is inferred from code and screenshots; it was not reproduced off-device. Fix: the theme switch no longer touches the native night mode (same change as 1), not a per-button patch. Every test now asserts `Appearance.setColorScheme` is never called. The Button primitive is unchanged. If a clipped label still shows on device, the next suspect is the label's `flex-shrink` in `Button.tsx`.

3. **Re-check of e8068b2 ran stale code.** The coordinator's second device check of e8068b2 reproduced both bugs. Inspecting Metro on :8081 (started before round 3) showed its file watcher delivers no change events: a bundle graph built before an edit never updates. The device's bundle URL (Hermes bytecode, lazy) still contained `toColorSchemeOverride` and none of `setColorSchemePreference`, while a never-requested URL variant built from disk had the current code. A newly created file (`src/theme/color-scheme-preference.ts`) was also unresolvable, so the store was moved into the existing `src/theme/use-theme.ts` (same API). So the device has not yet run round 3; both device rows stay open until Metro is restarted and the steps are re-run.
